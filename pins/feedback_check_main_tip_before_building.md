The worktree-per-session discipline ([[project_handoff_archive_discriminator_collision]] siblings; CLAUDE.md) solves *file* collisions — two sessions' uncommitted edits no longer mix on `main`. It does **not** solve *work* collisions: nothing stops three session-lineages from independently building the same feature over the same window.

**Proven 2026-05-30 (session `7843b781`).** I built foxden SZZ-lite + found a corpus + ran the fox gate end-to-end — a clean, correct session — only to discover at merge-review that `main` was already at foxden **v1.2** from parallel lineages (v1.1 cleared the gate; v1.2 did 6-repo replication incl. the same repos I used, hit the *same* `_git` decode bug and fixed it identically, and reached a firmer "drop the fox" verdict). My branch was fully superseded. Net code delivered: zero (correctly — merging would have regressed v1.2). The build effort was duplicated; the worktree kept it from becoming a tangled `main`, but didn't keep me from doing redundant work.

**Why:** orient surfaces `related_sessions`, but it's easy to anchor on the *handoff you were handed* (here the v1 handoff `3cc8ad35`) and treat it as the current state — when `main`'s actual tip for that area has moved several versions past it via concurrent sessions. Continuity is work-centric and distributed ([[project_cross_session_coordination]]): the corpus + git history are the coordination layer, but only if you *read the current tip*, not just your inherited starting point.

**The refinement — dedup the mechanical, let the uncertain converge.** "Always check and never rebuild what's in flight" is right for *mechanical* work (implement a known spec, apply a known fix — a second copy is pure waste). It is *wrong* taken to the limit for *uncertain empirical* claims, because pushed there it would delete the very thing that made the foxden verdict trustworthy. Three lineages, in sealed worktrees with zero channel between them, independently reached "the LLM fox ties free churn → drop it." That's an n=3 *decorrelated* replication — and it is **stronger** evidence than the canon's deliberate same-context attestation, whose failure mode is exactly correlated judgment (the HBP Minyan worry, [[project_heavy_bobbin_protocol]]): the same model agreeing with itself for the same wrong reason inside shared context. Isolation guaranteed the opposite here. So the collision was *simultaneously* wasted build effort and the most rigorous corroboration the project has produced — the waste and the rigor are one event seen from two sides. I was the independent witness to another lineage's claim, which is [[feedback_builder_cannot_self_verify]] operating on the *work* rather than a single claim. The discriminator is the mechanical-vs-judgment line that runs through everything ([[feedback_verify_across_instances]]).

**How to apply:** on any known multi-session / active topic, before committing to a build (not at merge — at the *start*):
- `git log --oneline -15 main -- <area>/` for the area you're about to touch — has it moved past the handoff you're resuming from? Skim the 2–3 most-recent `handoff/sessions/*.json` whose topic matches, not just the one you inherited.
- If it's in flight, ask *what kind of work is it?* **Mechanical / settled** (known spec or fix) → don't rebuild; resume or extend theirs. **Uncertain / empirical** (does X actually beat Y? is this verdict real?) → an independent blind run is *evidence, not waste* — proceed deliberately as decorrelated replication, keep your context sealed from theirs (don't read their result first — that re-correlates you), and report convergence-or-divergence as the deliverable.
Cheap check, ~10s; the failure it prevents is a whole session of *accidentally-mechanical* duplication. Sibling to [[feedback_probe_before_build]] (probe the substrate before scoping) — same shape: a tiny read up front so you're building against the live picture, then choosing dedup-or-converge on purpose instead of by accident.

## Sharpening 2026-05-31 (sid8 `561330af`) — the start-of-task check goes stale *within* a single session

The foxden case above is *cross-session* staleness caught at merge: I anchored on an inherited handoff and missed that `main` had moved over days. This is a tighter, faster variant — **the check you ran correctly at task-start can go stale before you act, inside one conversation.**

A "which folder?" question (top-level `brief/` vs nested `handoff/brief/`). I oriented at T0, read the tip, formed a consolidation plan — all correct *at T0*. While we *talked it through*, a concurrent session did the entire consolidation and **committed it** (`d3bbdb8`: relocated the file, wrote the convention doc, removed the stray folder). I then started executing my now-obsolete plan and **clobbered the tracked doc that session had just written** (restored from HEAD, net damage zero — but only because I re-statused mid-way). The window between my read and my write was *minutes*, not days, and a whole feature landed inside it.

**Why this is its own failure, not just "check the tip":** the pin's "How to apply" says check at the *start* of a build. I did. The gap is that in a **hot directory** (several sessions writing the same subtree in one window — `handoff/brief/` had 4 sessions touch it on 2026-05-31), start-of-task freshness is not write-time freshness. This is the cross-session twin of [[feedback_no_fabricated_results]]'s core error: trusting a *stale snapshot* (a T0 read) as if it were *current ground truth*, instead of re-confirming at the moment of action.

**How to apply (additional):**
- In a hot dir, **re-status the exact target immediately before the first `Write`/`Edit`/`git add`** — not just at task start. `git status --short <dir>/ && git log --oneline -3 main -- <dir>/`. If a file you're about to create/modify already exists or was just committed, stop and read it: you may be about to clobber or duplicate.
- **Never `Write` a file in a hot dir without re-reading first** — `Write` overwrites; a concurrent session may have authored a better version since your plan formed (it had — the convention doc).
- The tell you're in this trap: your plan was formed *before* a discussion and you're now executing it *after*, without having re-looked. The discussion itself is elapsed wall-clock in which the shared tree moved.
