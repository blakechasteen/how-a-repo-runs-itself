The memory Stop hook (`~/para-bots/scripts/claude_hook_memory_commit.sh:68`) stages with **`git add .`** — the entire memory dir, not the firing session's files — then commits under the memory-agent key with message `memory: session <sid8> @ <ts>` (sid8 = whichever session's Stop fired, read from stdin) and **pushes to origin**. So under concurrency, the first session's Stop hook to fire after *any* session's edits sweeps them ALL into one commit stamped with the **committing** session's sid8. Git-layer provenance for memory edits records **committer, not author**.

**Proven 2026-06-05 (sid8 96c093bb, system-map verification).** A freepass found this session's four canon edits scattered: three pins committed under `6d43481b` (commit `3275ecc`), `MEMORY.md` under `2cfb4747` (`44441d8`); 96c093bb's own hook commit (`053479a`) caught ~none of them. ~4 concurrent sessions that night. The memory-agent **key** attribution stayed correct (content SSH-signed by the agent, not Blake — the L1 fix holds); only the **session id** in the commit message is wrong.

**Why:** the provenance substrate (`Session:` trailer, `provenance.py`, `reattest`) attributes work commit→session. For the *repo* that's sound — `prepare-commit-msg` stamps each commit with its authoring session. For the *memory* dir the `git add .` model breaks it: `reattest` watching a pin would interrogate the **wrong** session about an edit it never made. Silent, and it recurs in every multi-session window — which is now the norm (auto-wire-every-session put many Claude sessions on the shared dir at once).

**Amendment (2026-06-13 · sid8 28d36080) — the same bug also flattens *recency*, not just *authorship*.** Building the MEMORY.md spine/catalog split ([[project_memory_spine_catalog_split]]) I used git last-commit-date per pin as the demotion rule's recency signal — and ~32 of 121 pins came back stamped the identical `2026-05-25`. Not 32 same-day edits: one bulk `git add .` stamping every swept file with the commit date. So git-commit-date ≠ when a pin's content last changed. A 21-day window swept 75/121 pins into 'active' (empty catalog); the cutoff had to drop to ~10d to clear that floor, and stays noisy. Same root cause as above — bulk `git add .` destroys per-pin provenance — but the flattened dimension is the *content-change date* rather than the *sid8*. General rule: **any per-pin metadata read off git history is corrupted by the bulk-commit hook; trust what's written _in_ the pin, not what git records _about_ it.**

**How to apply:**
- Editing a memory pin during a possibly-concurrent session: **sign the edit in-content with your `sid8`** (the session-signing discipline in CLAUDE.md), phrased as a fact about *authorship* so it stays true even if the hook misattributes the commit. Do not trust the commit's session id for memory provenance.
- **Do not** manually `git commit` the memory dir to "fix" attribution — that signs content with Blake's personal key and re-introduces the exact L1 false-attribution the canon fixed ([[project_siloing_as_separation_of_powers]]). Let the hook commit; carry truth in-content.
- Real fix is hook-side (parked, not built): stage only files touched since session-start (explicit path list / scoped `git add`), or stamp the authoring sid8 per file. The line to change is `git add .` at `claude_hook_memory_commit.sh:68`.
- Deriving per-pin **recency** (or any per-file metadata) from git history is unreliable here — the bulk `git add .` flattens commit dates. Use an authored frontmatter date instead. (Forced the [[project_memory_spine_catalog_split]] recency window down to ~10d.)
